# 02 — The Database Layer

> ### TL;DR — the 6 things you must be able to say
>
> 1. **Three tables** — `users` → `hosted_zones` → `dns_records`, two one-to-many hops.
> 2. **One row per record *set*** — all its values live in one `value TEXT`, newline-separated.
> 3. **The database enforces almost nothing** — PKs, `NOT NULL`, two unique indexes; every DNS rule is Python.
> 4. **`ON DELETE CASCADE` is decorative** — `PRAGMA foreign_keys` is `0`; the ORM's `delete-orphan` does the deleting.
> 5. **NULL `ttl` means "alias record"** — which is why the column deliberately has no default.
> 6. **No Alembic** — `create_all()` plus one hand-rolled `ALTER TABLE`, and that is where the schema drift comes from.
>
> **Read** §1–§8 (~25 min — this is the densest file in the set; §3 is the part that
> matters most). **Look up** everything under 🔎 Reference — never read it linearly.

Study notes for explaining the data model of the Route 53 clone in an interview, written for
someone fluent in **MongoDB / Mongoose** who is new to **SQL and SQLAlchemy**. Every factual claim
cites `file:line`; everything about the live database was read from `backend/route53.db` opened
read-only (`sqlite3.connect('file:route53.db?mode=ro', uri=True)`). **Jargon is defined on first
use** — look for the `→` callouts.

## 1. The 30-second version

Three tables — `users`, `hosted_zones`, `dns_records` — in SQLite, mapped with the SQLAlchemy ORM
(`backend/app/models.py`). A user owns many hosted zones; a hosted zone owns many DNS records; a
record's `value` column holds *all* the values of a record set, newline-separated, rather than one
row per value. The schema is deliberately thin: SQLite enforces only primary keys, `NOT NULL` and
two unique indexes, while every DNS-specific rule — record-type whitelist, TTL range, CNAME
exclusivity, the one-record-set-per-`(zone, name, type)` rule, ownership scoping — lives in Pydantic
schemas and route handlers in Python. There is no Alembic; tables come from
`Base.metadata.create_all()` at `backend/app/main.py:13` plus a hand-rolled `run_migrations()` at
`backend/app/main.py:16-21`. That last decision is the source of the one real piece of schema drift
in the project, which §3 covers honestly.

## 2. The three tables

| Table | Live rows | What it is | Keys that matter |
| --- | --- | --- | --- |


> **Readability trap you must be ready to explain.** `hosted_zones.zone_id` is a **VARCHAR** — the
> public, Route 53-style ID such as `ZKB406Z10S64QY`, generated at
> `backend/app/routes/zones.py:18-21`. `dns_records.zone_id` is an **INTEGER** — the foreign key to
> `hosted_zones.id` (`backend/app/models.py:70`). Same name, different things, never
> interchangeable: `get_zone_or_404` at `backend/app/routes/records.py:31-39` filters on
> `HostedZone.id`, the integer, even though the URL path segment is also spelled `zone_id`. Asked
> "what would you rename first?", this is a great answer — rename the string one `public_zone_id`.

> → **Surrogate key**: a primary key with no business meaning, generated by the database (here, an
> auto-incrementing integer `id`). The opposite is a *natural key* — a column already meaningful,
> like an email address; Mongo's `_id` ObjectId is a surrogate key too. This schema uses surrogate
> `id` everywhere and keeps the meaningful identifiers (`users.email`, `hosted_zones.zone_id`) as
> separate unique columns.

**Zone names are unique per owner, not globally.** Two of the six live zones are both
`civicvoice.xyz.` under different users, and that is correct: the check at
`backend/app/routes/zones.py:115-124` filters on `HostedZone.name == payload.name` **and**
`HostedZone.owner_id == current_user.id`. Two AWS accounts really can both host `example.com`.

### 2.1 `default=` vs `server_default=`

Worth memorising, because it explains several oddities later:

| | Where it runs | Appears in `CREATE TABLE`? | Applies to raw SQL inserts? |
| --- | --- | --- | --- |
| `default="Public"` | Python, at flush time | **no** | **no** |
| `server_default=func.now()` | SQLite, at insert time | **yes** (`DEFAULT CURRENT_TIMESTAMP`) | yes |
| `onupdate=func.now()` | emitted into the `UPDATE` statement | no | no |

Verified: `PRAGMA table_info(users)` returns `(4, 'created_at', 'DATETIME', 0, 'CURRENT_TIMESTAMP', 0)`
— a real SQL default, from `server_default=func.now()` at `backend/app/models.py:40` — while
`hosted_zones.type` (`default="Public"`, `backend/app/models.py:52`) returns
`(3, 'type', 'VARCHAR', 1, None, 0)`, **no** SQL default at all.

> **Mongoose analogy.** `default: "Public"` in a Mongoose schema is also applied by the driver in
> JavaScript, not by MongoDB, so SQLAlchemy's `default=` is the direct equivalent. There is no
> Mongoose equivalent of `server_default=`: Mongo has no DDL to put it in.

### 2.2 The `ttl` column has no default *on purpose*

The single best small design story in the schema — quote the comment verbatim:

```python
    # No column default: SQLAlchemy applies one whenever the attribute is None at
    # flush time, which silently rewrote the NULL that marks an alias record as 300.
    # RecordCreate.ttl already defaults to 300 when the client omits it, so the only
    # case the column default served is still covered.
    ttl = Column(Integer, nullable=True)
```
`backend/app/models.py:73-77`

1. NULL `ttl` means *alias record*. An alias points at an AWS endpoint (an ELB hostname, a
   CloudFront distribution) and Route 53 answers with the **target's** value and the **target's**
   TTL, so an alias has no TTL of its own — the docstring of `validate_alias_target` at
   `backend/app/schemas.py:513-521` spells this out.
2. A SQLAlchemy `default=300` runs in **Python at flush time whenever the attribute is `None`**, so
   it cannot tell "the caller omitted TTL" from "the caller deliberately set NULL because this is an
   alias" — it would rewrite every alias's NULL to 300 on insert, destroying the flag.
3. The default therefore moved up into Pydantic, where the cases *are* distinguishable:
   `ttl: Optional[int] = Field(default=300, ge=TTL_MIN, le=TTL_MAX)` (`backend/app/schemas.py:589`).
   An omitted field gets 300; an explicit `null` stays `None`.

The flag is read all over the app: the list filter at `backend/app/routes/records.py:168-172`
implements the console's Alias / Non-alias filter as `DNSRecord.ttl.is_(None)` / `.isnot(None)`, and
the create/update path branches on it at `backend/app/schemas.py:614-618` and
`backend/app/routes/records.py:57-60` to decide whether `value` is an alias target or type-specific
rdata. **Honest caveat**: overloading NULL as a boolean flag is clever but implicit — §7.2 has the
for/against and the fix.

## 3. Keys and constraints: database vs application

**The most important section, and the one most likely to earn or lose you the interview.** The
headline: *the database enforces almost nothing; Python enforces almost everything.* (~5 min)

### 3.1 What SQLite actually enforces in the live file

Read directly from `sqlite_master` and the `PRAGMA`s:

| Guarantee | Enforced by | Verified how |
| --- | --- | --- |
| `users.id`, `hosted_zones.id`, `dns_records.id` are unique non-null integers | `PRIMARY KEY (id)` → SQLite rowid alias | `EXPLAIN QUERY PLAN SELECT * FROM users WHERE id=1` → `SEARCH users USING INTEGER PRIMARY KEY (rowid=?)` |
| `users.email` is globally unique | `CREATE UNIQUE INDEX ix_users_email ON users (email)` | `sqlite_master` |
| `hosted_zones.zone_id` is globally unique | `CREATE UNIQUE INDEX ix_hosted_zones_zone_id ON hosted_zones (zone_id)` | `sqlite_master` |
| `NOT NULL` on `users.email`, `users.hashed_password`, `hosted_zones.zone_id/name/type`, `dns_records.zone_id/name/type/value` | column constraints | `PRAGMA table_info` |
| `created_at` is stamped even on a raw SQL insert | `DEFAULT CURRENT_TIMESTAMP` | `PRAGMA table_info` |
| **`dns_records.zone_id` points at a real zone** | ❌ **NOT enforced** | `PRAGMA foreign_keys` → `0` |
| **`hosted_zones.owner_id` points at a real user** | ❌ **no FK exists at all** | `PRAGMA foreign_key_list(hosted_zones)` → empty |

#### The drift: `owner_id` has no FK and no index in the live database

The model says one thing, the file says another. Compiling the metadata fresh with SQLAlchemy's
`CreateTable` emits `FOREIGN KEY(owner_id) REFERENCES users (id) ON DELETE CASCADE` plus
`CREATE INDEX ix_hosted_zones_owner_id`. The live `backend/route53.db` has `owner_id INTEGER`
bolted bare onto the end of the table, and its indexes are exactly `ix_hosted_zones_id`,
`ix_hosted_zones_name`, `ix_hosted_zones_zone_id` — **no `ix_hosted_zones_owner_id`** (both DDL
dumps: 🔎 **R2**). Two facts about the tools compound:

1. `Base.metadata.create_all(bind=engine)` at `backend/app/main.py:13` **only creates tables that
   do not exist**; it never alters one. This database predates `owner_id`, so `hosted_zones`
   already existed and `create_all` skipped it entirely.
2. The catch-up migration is a single `ALTER TABLE ... ADD COLUMN`:

```python
def run_migrations():
    """Lightweight SQLite migrations for columns added after the DB was first created."""
    with engine.begin() as conn:
        cols = [row[1] for row in conn.execute(text("PRAGMA table_info(hosted_zones)"))]
        if "owner_id" not in cols:
            conn.execute(text("ALTER TABLE hosted_zones ADD COLUMN owner_id INTEGER"))
```
`backend/app/main.py:16-21`

   SQLite's `ALTER TABLE ADD COLUMN` **cannot add a foreign key** to an existing table, and this
   statement adds no index either. The only way to add a FK to an existing SQLite table is the
   twelve-step "create new table, copy rows, drop old, rename" dance — exactly what Alembic
   generates for you.

The column is also `nullable=True`, and has to be: `ADD COLUMN` on a non-empty table cannot add a
`NOT NULL` column without a default, and existing rows had no owner. That nullability is what
`adopt_orphan_zones` (`backend/app/main.py:24-34`) exists to clean up. Spoken version: §8 Q12. The
README compounds it — `README.md:298` documents `owner_id` as *"FK → `users.id` (CASCADE),
indexed"*, true of the model and false of the deployed file.

#### `PRAGMA foreign_keys` is `0` — the cascade is inert DDL

`dns_records` **does** carry a real foreign key in the live file —
`FOREIGN KEY(zone_id) REFERENCES hosted_zones (id) ON DELETE CASCADE`, and
`PRAGMA foreign_key_list(dns_records)` confirms it with `on_delete = CASCADE`. But `PRAGMA
foreign_keys` returns `0`: **SQLite disables foreign-key enforcement per connection, by default,
for backwards compatibility.** Nothing in this codebase turns it on — no `PRAGMA foreign_keys=ON`
anywhere, no SQLAlchemy `connect` event listener — and a *fresh* engine built the same way as
`backend/app/database.py:10-13` also reports `0`. So the `ON DELETE CASCADE` is decorative: records
survive their zone at the SQL level, and what actually deletes them is the **ORM** cascade (§4).

> → **Cascade**: "when the parent row goes, do something to the child rows." `ON DELETE CASCADE`
> means the database deletes the children automatically. Mongo has no equivalent — you write the
> second `deleteMany` yourself or use a Mongoose `pre('remove')` / `post` middleware hook.
> SQLAlchemy's `cascade="all, delete-orphan"` is much closer to that Mongoose middleware than to
> real SQL `ON DELETE CASCADE`: application-side, and it only runs when you go through the ORM.

**The fix** (one line, and you should say it): a connect listener so every pooled connection turns
FKs on — then rebuild the DB, or run the table-rebuild migration, so `owner_id` gets its real FK.

```python
from sqlalchemy import event

@event.listens_for(engine, "connect")
def _fk_on(dbapi_conn, _):
    dbapi_conn.execute("PRAGMA foreign_keys=ON")
```

#### Why the distinction matters — give all three reasons

**(a) Error quality.** A `UNIQUE` violation surfaces as `IntegrityError: UNIQUE constraint failed:
dns_records.zone_id, dns_records.name, dns_records.type` — useless to a user. The application check
produces `"A CNAME record for 'www.example.com.' already exists."`
(`backend/app/routes/records.py:100-110`) with a proper `409 Conflict`. The mature answer is
**both**: check in Python for the message, keep the constraint as the backstop.

**(b) Some rules genuinely cannot be constraints.** The docstring of `check_record_set_conflicts` —
*"Enforce the two rules the schema layer can't check, because both need other rows."*
(`backend/app/routes/records.py:72`) — makes the argument for you. "A CNAME may not coexist with
*any* other record type at the same name" is a cross-row predicate: no `UNIQUE` index expresses it,
you'd need a trigger or an exclusion constraint.

**(c) Nothing else can write to this database.** With every rule in Python, the invariants hold only
for traffic through FastAPI — a `sqlite3` shell, a repair script, a background job or a second
service can all insert garbage. Whether that's acceptable is a *scope* decision, not a correctness
one, and saying so out loud makes it sound deliberate rather than accidental.

#### TOCTOU: the uniqueness check has a race

> → **TOCTOU** = "Time Of Check To Time Of Use": you check a condition, then act on it, and
> something changes in between. Any `if (!await Model.findOne(...)) await Model.create(...)` in
> Mongoose has the same shape — it's the check-then-act pattern, not a SQL-specific problem.

The sequence at `backend/app/routes/records.py:207-219`:

```
t0  Request A:  SELECT ... WHERE zone_id=1 AND name='www.example.com.' AND type='A'   → 0 rows
t1  Request B:  SELECT ... WHERE zone_id=1 AND name='www.example.com.' AND type='A'   → 0 rows
t2  Request A:  INSERT ...                                                            → ok
t3  Request B:  INSERT ...                                                            → ok
    result: two 'A' record sets for www.example.com. — the exact state the rule forbids.
```

With a real `UNIQUE (zone_id, name, type)` index, t3 fails with an `IntegrityError` and the
invariant survives any interleaving. Without it, it's only as good as the scheduler.

**Be precise about why this hasn't bitten in practice** (don't overclaim "SQLite prevents it"): the
deployment is a single Uvicorn process serving a demo, so two writes to the same `(zone, name,
type)` landing in the same few microseconds is effectively impossible; and the database is in
rollback-journal mode (`PRAGMA journal_mode` → `delete`), where SQLite allows **only one writer at
a time**, database-wide — reads overlap, but once one connection takes the RESERVED lock to write,
a second trying to upgrade from read to write gets `SQLITE_BUSY` / `database is locked`. So the
realistic failure mode under load is **an ugly 500 "database is locked"**, not silent duplication:
SQLite narrows the window without closing it, converting a correctness problem into an availability
problem rather than fixing it.

**The fix, in one line:**

```python
__table_args__ = (UniqueConstraint("zone_id", "name", "type", name="uq_record_set"),)
```

then catch `IntegrityError` in `create_record` and re-raise the same friendly 409 — you keep the
message *and* get the guarantee. (On SQLite you must recreate the table to add it; on Postgres it's
a one-line migration, another argument for §5.) **And there is a live, non-hypothetical instance of
this bug** — §6.3 on `autoflush=False`, where the same pattern loses to a *single-threaded* loop.

## 4. Relationships and cascade

```python
    records = relationship("DNSRecord", back_populates="zone", cascade="all, delete-orphan")
    owner = relationship("User")
```
`backend/app/models.py:58-59`

```python
    zone = relationship("HostedZone", back_populates="records")
```
`backend/app/models.py:84`

### 4.1 `relationship()` vs Mongoose `populate()`

| | Mongoose | SQLAlchemy |
| --- | --- | --- |
| Declare the link | `ref: 'HostedZone'` on an ObjectId field | `ForeignKey("hosted_zones.id")` on the column |
| Traverse the link | `.populate('zone')` — **explicit, at query time** | `record.zone` — **implicit, on attribute access** |
| When the extra query fires | when you ask for it | the first time you touch the attribute (default `lazy="select"`) |
| Both directions stay in sync in memory | no | yes, via `back_populates` |

So **a `relationship()` is roughly Mongoose's `populate()`, but resolved lazily on attribute access
instead of being requested up front** — exactly what causes the N+1 in §8 Q9. In Mongoose you can't
accidentally trigger a query by reading a property; in SQLAlchemy you can, and you will.
`back_populates` wires the pair bidirectionally: `zone.records.append(rec)` in memory also sets
`rec.zone`, with no round trip. Mongoose has no equivalent; you'd set both sides by hand.

### 4.2 What actually happens on `db.delete(zone)`

`delete_zone` at `backend/app/routes/zones.py:250-279` ends with `db.delete(zone)` then
`db.commit()`. Because FK enforcement is off (§3.2) the database contributes nothing; the ORM does
all the work. SQL captured on a throwaway database (never `route53.db`), zone with 3 records:

```
SELECT hosted_zones ... WHERE id = ?        -- load the parent
SELECT dns_records  ... WHERE zone_id = ?   -- ← cascade forces the children to load
DELETE FROM dns_records WHERE id = ?        -- executemany, one row per record
DELETE FROM hosted_zones WHERE id = ?
```

Read that carefully: **`cascade="all, delete-orphan"` makes SQLAlchemy `SELECT` every child into
memory just to `DELETE` it individually.** For a zone with 5,000 records that's one big SELECT plus
5,000 parameter sets, where real `ON DELETE CASCADE` would be a single statement and no SELECT — the
concrete cost of the inert FK. The two halves: **`all`** propagates
save/update/merge/refresh/**delete** from parent to children; **`delete-orphan`** additionally
deletes a child *disassociated* from its parent (`zone.records.remove(rec)`), which would otherwise
be left behind with a dangling `zone_id`.

> **Mongoose analogy**: `cascade="all, delete-orphan"` ≈ a `pre('deleteOne', {document: true})`
> hook running `DNSRecord.deleteMany({ zone: this._id })`. Same layer (application), same caveat: it
> only fires when you go through the ORM/ODM. A raw `db.execute(delete(HostedZone).where(...))`
> bypasses it entirely, exactly as `HostedZone.collection.deleteOne()` bypasses a Mongoose hook.

### 4.3 The asymmetry: `owner` has no cascade

`owner = relationship("User")` at `backend/app/models.py:59` has **no** `cascade` argument (so it
gets SQLAlchemy's default, `"save-update, merge"` — no delete) and, in the live DB, **no** FK either
(§3.1). Verified on a throwaway DB:

```
db.delete(user); db.commit()
  → SELECT users ... ; DELETE FROM users WHERE id = ?
  → zones left after deleting their owner: 1, owner_id values: [1]
```

Deleting a user leaves their zones behind, pointing at a user ID that no longer exists. Nothing in
the app deletes users today, so this is latent rather than live — but it's the honest answer to
"what happens when a user is deleted?", and the fix is the one from §3.2 (turn FKs on, add the real
FK) plus `cascade="all, delete-orphan"` on a proper `User.zones` back-reference. It is a *different*
problem from the one `adopt_orphan_zones` solves (`backend/app/main.py:24-34`): that function
handles zones whose `owner_id` is **NULL** — rows predating the ownership feature — and reassigns
them to the demo account so they don't leak into brand-new accounts, via
`db.query(HostedZone).filter(HostedZone.owner_id.is_(None)).all()` (`backend/app/main.py:30`). A
dangling non-NULL `owner_id` slips straight past that filter.

## 5. The migration story

### 5.1 There is no Alembic

Schema management is two things. First, `models.Base.metadata.create_all(bind=engine)` at
`backend/app/main.py:13`, which runs at **import** time, before the app object even exists. Second,
`run_migrations()` (`backend/app/main.py:16-21`, quoted in full in §3.1), called from the startup
hook:

```python
@app.on_event("startup")
def on_startup():
    run_migrations()
    db = SessionLocal()
    try:
        seed_demo_user(db)
        adopt_orphan_zones(db)
        # Last, so adopted orphan zones count as existing content and suppress seeding.
        seed_demo_content(db)
    finally:
        db.close()
```
`backend/app/main.py:67-77`

Note the ordering comment: `seed_demo_content` runs last so a zone adopted by `adopt_orphan_zones`
counts as existing content and suppresses seeding. The idempotency guard is
`backend/app/services/demo_seed.py:239` — `if db.query(HostedZone).filter(HostedZone.owner_id ==
demo.id).count() > 0: return`. You can see it working in the live DB: the demo user (id 1) already
owns `vprofile.in.`, `example.com.`, `civicvoice.xyz.` and `shubh-gupta.in.`, so
`seed_demo_content` has never fired locally — none of the ten `example.com.` demo records from
`backend/app/services/demo_seed.py:39-90` are present, only the two default NS/SOA rows.

### 5.2 What `create_all()` does and does not do

| Situation | `create_all()` |
| --- | --- |
| Table missing | creates it, with every column, index and FK from the model |
| Table exists, model gained a column | **does nothing** |
| Table exists, model gained an index | **does nothing** |
| Table exists, column type changed | **does nothing** |
| Column dropped from the model | leaves it in the DB forever |

It is `CREATE TABLE IF NOT EXISTS`, nothing more: no concept of a version, no history, no
down-migration, no ordering. `PRAGMA user_version` on the live file is `0` — no schema version is
recorded anywhere. `run_migrations()` patches exactly one gap, the `owner_id` column, and its limits
are real: **one column, hard-coded** (the next needs another hand-written `if`); **additive only**
(no renames, type changes, drops or data backfills); **no foreign keys or indexes**, because
SQLite's `ADD COLUMN` can't express them (§3.1) — the root cause of the drift; **no down path**; and
**not recorded** — it re-runs the `PRAGMA table_info` probe every boot, which is correct, but means
"has this migration run?" is answered by inspecting the schema rather than by a version table.

### 5.3 The honest reason it was acceptable here

Not "migrations don't matter" — a specific, verifiable property of the deployment: **there is no
durable database to migrate.** The module docstring of the seeder says it outright:

```python
"""Populates the demo account with realistic hosted zones and records.

Render's free plan gives the service an ephemeral filesystem, so route53.db is rebuilt
from scratch on every deploy and every wake-from-idle. Seeding therefore has to happen
on startup rather than once via a migration or a marker file — there is nowhere durable
to record that it already ran, so the presence of the demo user's own zones is the flag.
"""
```
`backend/app/services/demo_seed.py:1-7`

The deploy blueprint agrees at `render.yaml:7-10`: the free plan's ephemeral filesystem means the
SQLite file is recreated on every deploy or wake-from-idle, startup seeding is what keeps the demo
populated, and durable storage means a paid plan with a disk mounted at `/data` plus
`DATABASE_URL=sqlite:////data/route53.db` (four slashes).

So in production every boot creates the schema from scratch via `create_all()` — which *does* emit
the FK and the `owner_id` index. **The drift only exists in long-lived local databases like
`backend/route53.db`, carried forward since before ownership was added.** Much better than "I
forgot", and checkable: the local file's `hosted_zones` rows are dated `2026-06-19`, before the
ownership feature existed.

**What I'd change the moment the DB became durable** — attach a Render disk, and the first migration
becomes load-bearing: `pip install alembic`, `alembic init`, `alembic revision --autogenerate` from
the existing models; `alembic stamp head` on the current DB so the baseline is recorded rather than
replayed; delete the `create_all()` call and `run_migrations()`, making `alembic upgrade head` the
release command; then write the table-rebuild migration that finally gives `owner_id` its FK and
index. `--autogenerate` diffs the model metadata against the live database and writes the `ALTER`s —
it would have caught this drift on the first run, the cleanest illustration of why the tool exists.

## 6. Engine and session setup

All four lines that matter are in `backend/app/database.py`. (~5 min)

### 6.1 The engine

```python
DATABASE_URL = os.getenv("DATABASE_URL", "sqlite:///./route53.db")

engine = create_engine(
    DATABASE_URL,
    connect_args={"check_same_thread": False}  # SQLite only
)
```
`backend/app/database.py:8-13`

`DATABASE_URL` comes from the environment with a SQLite fallback, so swapping to Postgres is a URL
change plus dropping `connect_args` (§6.4 covers what else breaks). And `create_engine` is **not** a
connection: it's a factory plus a connection pool — closer to Mongoose's `mongoose.connect()`
managing an internal driver pool than to a single socket — created once at import, living for the
whole process.

#### Why `check_same_thread: False`

Python's stdlib `sqlite3` driver refuses by default to let a connection object be used from any
thread other than the one that created it, raising `ProgrammingError: SQLite objects created in a
thread can only be used in that same thread`. That default is fatal here: an `async def` endpoint
runs on the event loop, but a plain `def` endpoint — which is **every endpoint in this project**
(`backend/app/routes/zones.py:66`, `:110`, `:144`, …; `backend/app/routes/records.py:140`, `:198`,
…) — is run by Starlette in a **worker threadpool** so it can block without stalling the loop.
SQLAlchemy's pool is process-wide, so a connection first opened on threadpool worker #3 is handed to
worker #7 later: different thread, same connection object → the driver would raise.

**Is that safe?** Yes — and say *why*, not just "SQLAlchemy handles it": raw `sqlite3` connections
are unsafe to share *concurrently*, but the default `QueuePool` checks a connection **out** to
exactly one thread at a time and only returns it on close, so no two threads ever hold the same
connection at once, and `get_db()` guarantees the check-in happens (§6.5).

The comment `# SQLite only` at `backend/app/database.py:12` matters: passing `check_same_thread` to
a Postgres driver raises `TypeError`, so this line must become conditional on the URL scheme before
switching backends. The test suite already does it properly at
`backend/tests/test_records_routes.py:35-39`, adding `poolclass=StaticPool` so a per-test SQLite
file is shared correctly across the TestClient's threads.

### 6.2 The session factory

```python
SessionLocal = sessionmaker(autocommit=False, autoflush=False, bind=engine)
```
`backend/app/database.py:15`

> **Mongoose analogy.** There is no Mongoose equivalent of a `Session` — this is the piece that
> feels most alien coming from Mongo. A SQLAlchemy `Session` is a **unit of work** plus an
> **identity map**: it batches pending changes, tracks which objects it has already loaded (so
> `db.query(User).get(1)` twice returns the *same Python object*), and flushes them as one
> transaction. Mongoose has no such buffer — every `.save()` is its own round trip. Think of it as
> an in-memory staging area you eventually `commit()`.

**`autocommit=False`** is the SQLAlchemy 2.x default and the only supported mode: work is
transactional, nothing is durable until `db.commit()`. That's what makes `seed_demo_content`'s
`db.rollback()` at `backend/app/services/demo_seed.py:290` meaningful — a half-applied seed is
discarded rather than persisted. **`autoflush=False`** is the non-default one, and the interesting
one.

### 6.3 `autoflush=False` — the flag with a real bug behind it

**Flush ≠ commit.** *Flush* pushes pending Python objects out as `INSERT`/`UPDATE` statements inside
the open transaction; *commit* makes them durable. With SQLAlchemy's default `autoflush=True` the
session flushes automatically **right before any query**, so a query always sees your own pending
writes ("read-your-writes"). `False` turns that off: a `db.add()` is invisible to a later
`db.query()` in the same session until you flush or commit by hand.

That has a concrete consequence in `import_zone_file` (`backend/app/routes/records.py:355-425`),
whose loop is check-then-act, once per parsed record:

```python
        existing = (
            db.query(DNSRecord)
            .filter(DNSRecord.zone_id == zone_id, DNSRecord.name == name, DNSRecord.type == rtype)
            .first()
        )
        if existing:
            ...
            existing.value = value
            existing.ttl = ttl
            updated += 1
        else:
            db.add(DNSRecord(
```
`backend/app/routes/records.py:400-413`

with a single `db.commit()` after the whole loop (`backend/app/routes/records.py:424`). The trap:
`parse_zone_file` groups by the **raw** parsed name (`backend/app/services/bind_parser.py:124-130`),
while `normalize_record_name` lowercases the name *afterwards*, at
`backend/app/routes/records.py:389`. So a zone file containing both `WWW.example.com.` and
`www.example.com.` produces **two** parser groups that **normalise to the same name**. Iteration 1
finds nothing → `db.add(...)`, `created += 1`; iteration 2 queries with `autoflush=False`, so it
does **not** see iteration 1's pending INSERT → finds nothing → `db.add(...)` again. Reproduced
against a throwaway database using the project's own models and validators:

```
autoflush=False: created=2 updated=0 -> rows named www.example.com. = 2
autoflush=True:  created=1 updated=1 -> rows named www.example.com. = 1
```

Two rows for one record set — the exact state `check_record_set_conflicts` exists to prevent,
produced by a **single-threaded loop with no concurrency at all**. It is the TOCTOU race from §3.2,
except the "concurrent" writer is the previous iteration of the same `for` loop, and the missing
`UNIQUE` index means nothing stops it.

**Three independent fixes, any one of which closes it** (say all three; it shows you understand the
layering): add the `UniqueConstraint("zone_id","name","type")`, the durable fix that catches every
path; drop `autoflush=False` (or `db.flush()` at the end of each iteration) so the query sees
pending rows; or normalise the name **before** grouping, in `parse_zone_file`, so the two spellings
merge into one record set as intended.

**Why was `autoflush=False` set at all?** A common FastAPI-tutorial default with a legitimate
upside — predictability: with autoflush on, a read can trigger a write and raise an `IntegrityError`
from a line that only looks like a `SELECT`, which is genuinely confusing. Honest framing: *"it's
defensible, but it removes read-your-writes, and this codebase has one check-then-act loop that
depended on read-your-writes without knowing it."*

### 6.4 What else changes on Postgres

Worth having ready, because "how would you scale this?" leads straight here:

| | SQLite today | Postgres |
| --- | --- | --- |
| `connect_args={"check_same_thread": False}` | required | invalid — must be removed |
| `String` with no length | fine (lengths ignored) | fine for `VARCHAR`/`TEXT`; MySQL would reject it |
| `PRAGMA foreign_keys` | off by default | FKs always enforced |
| `ilike` (`backend/app/routes/zones.py:79`, `backend/app/routes/records.py:158-160`) | works, because SQLite `LIKE` is case-insensitive for ASCII anyway | genuinely case-insensitive; consider a `citext`/functional index |
| Concurrent writers | one, database-wide | many, row-level locks |
| `DATETIME` | stored as TEXT (`typeof(created_at)` → `'text'`) | real `timestamptz` |

That last row is worth knowing: SQLite has **no** date type. `created_at` is a string.

> → **Type affinity**: SQLite doesn't enforce column types, it only *prefers* them — a column
> declared `INTEGER` will happily store the string `"banana"`. Declared types map to five affinities
> (TEXT, NUMERIC, INTEGER, REAL, BLOB) describing how SQLite *tries* to convert a value before
> storing it. Verified on the live DB: `typeof(name)` → `text`, `typeof(ttl)` → `integer`,
> `typeof(created_at)` → **`text`**. `VARCHAR(50)` is not a length limit — the `50` is ignored
> entirely. So `String` columns with no length are harmless here, but would need lengths on MySQL.

### 6.5 `get_db()` and why `finally` matters

```python
def get_db():
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()
```
`backend/app/database.py:20-25`

This is a **FastAPI dependency with yield**. Every route declares `db: Session = Depends(get_db)`
(e.g. `backend/app/routes/zones.py:73`), so FastAPI runs the generator up to the `yield`, injects
the session, runs the handler, then resumes the generator afterwards — including when the handler
raised.

**Why `finally` is not optional.** Without it — `db = SessionLocal()`, `yield db`, `db.close()` —
the close line is never reached when the handler raises, and this codebase raises `HTTPException`
constantly: 404 at `backend/app/routes/records.py:38`, 409 at `backend/app/routes/records.py:91-97`,
422 at `backend/app/routes/records.py:62`. The exception
propagates *into* the generator at the `yield`, the line after it never runs, and the session — plus
the pooled DB connection it has checked out — is never returned to the pool. That's a **connection
leak**: with the default `QueuePool` (`pool_size=5`, `max_overflow=10`), fifteen validation errors
exhaust the pool and every subsequent request hangs for `pool_timeout` seconds, then fails with
`TimeoutError: QueuePool limit of size 5 overflow 10 reached`. Because these are the *expected*,
everyday error paths, ordinary user mistakes would trigger the leak, not rare crashes.

The startup hook applies the same discipline manually (`backend/app/main.py:70-77`, quoted in §5.1)
because it isn't a request and has no `Depends`; and `seed_demo_content` never lets an exception
escape at all (`backend/app/services/demo_seed.py:279-293`), because *"an exception escaping here
would take the live API down over cosmetic demo data"* (`backend/app/services/demo_seed.py:282-283`).

## 7. Design decisions and trade-offs

Each is a place an interviewer can push. Have the for, the against, and the fix. (~5 min)

### 7.1 Newline-separated `value TEXT` instead of a child table

A DNS *record set* is `(name, type)` with **one or more** values — four NS records, three A records
behind a load balancer, two MX records with different priorities. This schema stores them as one row
whose `value` is `"ns-1.awsdns-1.com.\nns-2.awsdns-2.net.\n..."` (`backend/app/models.py:78`,
written at `backend/app/routes/zones.py:31-36`). The alternative is a third table:
`dns_records (id, zone_id, name, type, ttl)` 1 ── N `record_values (id, record_id, value)`.

| For the current design | Against |
| --- | --- |
| Matches the domain: Route 53's own API treats a record set as one addressable object, not N objects | `value` is unsearchable in SQL — you cannot ask "which zones point at `192.0.2.10`?" without `LIKE '%…%'` |
| Matches the UI: the console edits a record set in one multi-line textarea | No per-value constraints, no per-value uniqueness, no index on a value |
| Order is preserved for free (MX priority, SRV) — a child table needs an explicit `position` column | Validation must split and re-join: `validate_record_value` at `backend/app/schemas.py:487-510` splits on `\n`, validates each line, rejoins |
| Reads and writes are one row — no join, no N+1 for the common case | A `\n` inside a value would corrupt the encoding (safe today only because `_LABEL_RE` at `backend/app/schemas.py:149-150` excludes whitespace, and `_tokenize` at `:228-263` won't cross lines) |
| Import/export are trivial: `r.value.split("\n")` at `backend/app/routes/zones.py:223` and `:241` | Not first normal form. An interviewer *will* say "that's a denormalised list in a column" |

**Verdict to give:** *"A deliberate denormalisation that mirrors how the domain and the UI both model
a record set, and it makes every read a single row. The price is that values are opaque to SQL. I'd
move to a child table the moment I needed to query or index by value — a 'find every record pointing
at this IP' feature, or per-value weights for weighted routing."* Note the frontend already models it
as an array (`value: string[]` in the JSON export at `backend/app/routes/zones.py:223`), so the `\n`
encoding is purely a storage detail — a good sign it's a considered trade.

### 7.2 Nullable `ttl` as the alias flag

| For | Against |
| --- | --- |
| No extra column; the flag is where the semantics already are (an alias genuinely has no TTL) | It's an **implicit** boolean. `WHERE ttl IS NULL` doesn't read as "is an alias" to anyone new |
| Matches Route 53: alias records really do inherit the target's TTL | Two meanings collapse into one NULL: "alias" and "unknown/not set" become indistinguishable |
| Makes the filter trivial (`backend/app/routes/records.py:168-172`) | It forced the column-default footgun documented at `backend/app/models.py:73-76` |
| Round-trips cleanly through JSON (`ttl: null`) | Every consumer must know the convention, and it's only written down in comments |

**Fix:** add an explicit `is_alias = Column(Boolean, nullable=False, default=False)` and a
`CHECK (is_alias = 0 OR ttl IS NULL)` so the two can't disagree; then `ttl IS NULL` becomes a
consequence rather than the definition. *Honest note*: the live `backend/route53.db` has **zero**
rows with `ttl IS NULL` — no alias records have been created locally — so this path is exercised
only by the tests and the validators, not by live data I could show you.

### 7.3 Nullable `owner_id`

| For | Against |
| --- | --- |
| It had to be nullable — SQLite's `ADD COLUMN` can't add `NOT NULL` without a default to a table with existing rows | Every ownership filter now depends on `owner_id` being non-NULL, and the DB doesn't guarantee it |
| Let the ownership feature ship without a destructive rebuild | A zone created with a bug that skips `owner_id` becomes invisible to *everyone* — it matches no user's filter |
| `adopt_orphan_zones` (`backend/app/main.py:24-34`) cleans up the legacy rows on every boot | The clean-up runs forever; there's no point at which it's declared done |

**Fix:** once the data is clean, rebuild the table with `owner_id INTEGER NOT NULL REFERENCES
users(id) ON DELETE CASCADE`, flip `nullable=False` in the model, and delete `adopt_orphan_zones`.
That is one Alembic migration.

### 7.4 Stringly-typed enums, and two pieces of dead code

`backend/app/models.py:8-30` declares two Python enums — `ZoneType` (`PUBLIC = "Public"`,
`PRIVATE = "Private"`, `backend/app/models.py:8-10`) and `RecordType` (`A = "A"`, …,
`backend/app/models.py:13-30`). **Neither is ever used.** A repo-wide search finds them declared in
`backend/app/models.py` and then only in the *frontend's* unrelated TypeScript types
(`frontend/src/types/index.ts:10`, `:43`). No column is `Column(Enum(ZoneType))`; `hosted_zones.type`
and `dns_records.type` are both plain `String` (`backend/app/models.py:52`, `:72`). The real
whitelist lives in Pydantic at `backend/app/schemas.py:113-116`, duplicating the enum's contents,
and `from sqlalchemy import ... Enum` at `backend/app/models.py:1` is an unused import.

Second piece of dead code — **`private_zone`** (`private_zone = Column(String, default="No")`,
`backend/app/models.py:54`). Never read, never explicitly written anywhere in the backend; the only
other mention in the repo is the README's schema table at `README.md:303`. The Python-side
`default="No"` fills it on insert, so every row says `No` — including `vprofile.in.`, which is
`type='Private'`. **The live data literally contradicts itself**:

```
id  name            type      private_zone
1   vprofile.in.    Private   No          ← the two columns disagree
```

That's the best possible argument against a redundant column: given two sources of truth, they will
diverge, and here they already have.

| For string columns over a SQL `Enum` type | Against |
| --- | --- |
| SQLite has no native enum — SQLAlchemy's `Enum` becomes a `VARCHAR` + `CHECK` anyway | Adding a record type requires editing `VALID_RECORD_TYPES` **and** the unused enum **and** the frontend list |
| Adding a record type is a one-line set edit, no migration | Nothing stops a raw SQL insert writing `type='BANANA'` |
| Pydantic gives a far better error message than a `CHECK` violation | Three sources of truth (Python enum, Pydantic set, TS union) that can drift |

**Fix:** delete `ZoneType`, `RecordType`, `private_zone` and the unused `Enum` import; make
`VALID_RECORD_TYPES` the single source of truth and generate the frontend union from it (or from the
OpenAPI schema FastAPI already publishes at `/api/docs`).

### 7.5 The index situation is exactly backwards

Live indexes, from `sqlite_master`:

| Index | Table | Column | Verdict |
| --- | --- | --- | --- |
| `ix_users_id` | `users` | `id` | **redundant** |
| `ix_users_email` (UNIQUE) | `users` | `email` | correct — used on every request |
| `ix_hosted_zones_id` | `hosted_zones` | `id` | **redundant** |
| `ix_hosted_zones_name` | `hosted_zones` | `name` | reasonable |
| `ix_hosted_zones_zone_id` (UNIQUE) | `hosted_zones` | `zone_id` | correct |
| `ix_dns_records_id` | `dns_records` | `id` | **redundant** |
| — | `hosted_zones` | `owner_id` | **MISSING** (declared at `backend/app/models.py:48`, lost to `ALTER TABLE`) |
| — | `dns_records` | `zone_id` | **MISSING** (never declared) |

**Why the three `id` indexes are redundant.** All three models write
`id = Column(Integer, primary_key=True, index=True)` (`backend/app/models.py:36`, `:46`, `:69`), and
`index=True` is pure waste: in SQLite an `INTEGER PRIMARY KEY` **is** the table's rowid, so the table
itself is already a B-tree keyed by `id`. The planner proves it — `EXPLAIN QUERY PLAN SELECT * FROM
dns_records WHERE id=1` → `SEARCH dns_records USING INTEGER PRIMARY KEY (rowid=?)`. The index is
never chosen; it only costs write time and disk on every insert. (True on Postgres too, for a
different reason: a `PRIMARY KEY` implicitly creates a unique index, so `index=True` makes a second.)

**Why the two missing ones hurt.** `dns_records.zone_id` is filtered by **every single record
query**: list at `backend/app/routes/records.py:155`, get at `:233`, update at `:250`, delete at
`:306`, bulk delete at `:339`, import at `:402`, export at `backend/app/routes/zones.py:204`, and the
conflict check at `:84`. Without an index every one is a full table scan — `EXPLAIN QUERY PLAN`
returns `SCAN dns_records` for `WHERE zone_id = 1` and `SCAN hosted_zones` for `WHERE owner_id = 1`
(full plans in 🔎 R3). `SCAN` = read every row; `SEARCH ... USING INDEX` = B-tree descent. With 12
records and 6 zones that's free; at 100k records it's the difference between 1 ms and 200 ms, on the
hottest path in the app.

**Fix — three lines, biggest performance win available:**

```python
# models.py
id = Column(Integer, primary_key=True)                 # drop index=True, x3
zone_id = Column(Integer, ForeignKey(...), nullable=False, index=True)   # dns_records

# and the composite that serves the conflict check AND the uniqueness constraint:
__table_args__ = (
    UniqueConstraint("zone_id", "name", "type", name="uq_record_set"),
)
```

That last one is a twofer: a `UNIQUE (zone_id, name, type)` constraint **creates a backing index**,
so it simultaneously closes the TOCTOU hole from §3.2 *and* makes `check_record_set_conflicts`'s
`SELECT` (`backend/app/routes/records.py:83-87`) an index seek. It also subsumes the plain `zone_id`
index, because a composite index on `(zone_id, name, type)` serves any query filtering on its
**leftmost prefix** — `WHERE zone_id = ?` alone. *Caveat:* adding it would first require
de-duplicating any existing `(zone_id, name, type)` collisions, including any the §6.3 autoflush bug
created.

### 7.6 `String` with no length

Every text column is `String` or `Text` with no length (`backend/app/models.py` throughout). Fine on
SQLite, which ignores VARCHAR lengths entirely (§6.4). On MySQL, `VARCHAR` without a length is a DDL
error; on Postgres it's legal but you lose a cheap sanity check. The app-level limits do exist —
`MAX_NAME_BYTES = 255`, `MAX_LABEL_BYTES = 63` at `backend/app/schemas.py:127-128` — they're just not
in the schema. **Fix:** `String(255)` on `name` columns to match the DNS limit
`normalize_record_name` already enforces at `backend/app/schemas.py:546-550`.

## 8. "If they ask…"

Twelve questions with tight spoken answers, 30–60 seconds each; every one has a longer version
above if they dig. (~6 min)

**1. "Walk me through the schema."**

> Three tables. `users` holds the account and a bcrypt hash. `hosted_zones` is a DNS zone — `name`
> like `example.com.`, a Route 53-style public `zone_id`, and an `owner_id` pointing back at the
> user. `dns_records` holds the record sets: `name`, `type`, `ttl`, and a `value` column storing all
> of a record set's values newline-separated, plus an integer `zone_id` foreign key. One thing I'd
> rename: `hosted_zones.zone_id` is the public string ID and `dns_records.zone_id` is the integer
> foreign key — same name, different things, and that confused me while building it.

**2. "Why SQLite?"**

> Zero-configuration, single file, no service to run — right for a demo that has to be cloned and
> started in one command. The deployment reinforces it: Render's free tier has an ephemeral
> filesystem, so the DB is rebuilt from scratch on every deploy anyway; there was nothing durable to
> protect. I kept the access layer portable — SQLAlchemy ORM, `DATABASE_URL` from the environment —
> so switching to Postgres is a URL change plus removing the SQLite-only `check_same_thread` arg.
> What it costs me is one writer at a time database-wide, and no foreign-key enforcement unless I
> turn it on per connection.

**3. "How do you prevent one user seeing another's data?"**

> Every query is scoped by `owner_id` at the query level, not filtered after the fact. One helper,
> `get_zone_or_404`, fetches a zone by `id` **and** `owner_id == current_user.id` and raises 404 —
> not 403 — if either fails, so you can't probe for the existence of someone else's zone. Every
> record endpoint calls it first and then filters records by that zone's id, so record access is
> transitively scoped. The weakness is that it's convention: enforced by every handler remembering
> to do it, not by the database. Hardening it means row-level security on Postgres, or at minimum a
> shared base query so the filter can't be forgotten.

**4. "You have `ON DELETE CASCADE` on `dns_records.zone_id`. What happens when I delete a zone?"**

> Honest answer: not what the DDL says. `PRAGMA foreign_keys` is `0` — SQLite disables foreign-key
> enforcement per connection by default and nothing in my code turns it on — so that cascade never
> fires. What deletes the records is SQLAlchemy's `cascade="all, delete-orphan"`: on
> `db.delete(zone)` the ORM SELECTs every child into memory and issues an individual DELETE per row,
> then deletes the parent. Correct, but application-side, so a raw SQL delete would leave orphans,
> and for a large zone it's N statements where the database could do one. The fix is a four-line
> connect-event listener issuing `PRAGMA foreign_keys=ON`, plus `passive_deletes=True` so the ORM
> lets the database do the work.

**5. "Is `(zone_id, name, type)` unique?"**

> Logically yes, structurally no. There's no unique constraint — it's a SELECT-then-INSERT check in
> `check_record_set_conflicts`, which also handles the CNAME rules no index could express, like "a
> CNAME can't share a name with any other record type". That's a check-then-act race: two concurrent
> creates can both see zero rows and both insert. In practice SQLite's single-writer lock means the
> second usually gets `database is locked` rather than silently duplicating — but that's luck, not a
> guarantee. And I found a live instance with no concurrency at all: because `autoflush=False`, the
> zone-file import loop's lookup can't see rows it added earlier in the same loop, so two spellings
> of one name both insert. The right fix is a real `UNIQUE (zone_id, name, type)`, catching the
> `IntegrityError` and re-raising my friendly 409 — I keep the message, gain the guarantee, and the
> backing index removes a full table scan.

**6. "Why is `ttl` nullable with no default?"**

> NULL `ttl` is how I mark an alias record: an alias points at an AWS endpoint and Route 53 answers
> with the target's value and TTL, so it has no TTL of its own. I originally had `default=300` on
> the column and it silently rewrote every alias's NULL to 300 — a SQLAlchemy `default=` runs in
> Python at flush time whenever the attribute is `None`, and can't distinguish "the caller omitted
> this" from "the caller meant NULL". So the default moved up into Pydantic, where those cases *are*
> distinguishable: an omitted field gets 300, an explicit `null` stays `None`. There's a comment in
> `models.py` explaining exactly that so nobody re-adds it. Doing it again I'd add an explicit
> `is_alias` boolean plus a CHECK constraint, because overloading NULL is clever but implicit.

**7. "Why store multiple values in one TEXT column instead of a child table?"**

> It mirrors the domain: Route 53's API treats a record set as a single addressable object and the
> console edits it as one multi-line textarea, so one row per record set matches both. It gets me
> ordering for free — MX priority and SRV weight are positional — and keeps every read to a single
> row with no join. The cost is that `value` is opaque to SQL: I can't index it or answer "which
> records point at this IP" without a `LIKE '%…%'` scan, and it isn't first normal form. I'd
> normalise into a `record_values` child table the moment I needed to query or index by value, or
> when I wired up weighted routing where each value needs its own weight.

**8. "How would you scale this?"**

> Four steps, in order. **One**, move to Postgres — the ORM layer barely changes, and it buys real
> concurrent writes, enforced foreign keys and proper timestamp types instead of SQLite's
> one-writer-at-a-time and TEXT dates. **Two**, add the indexes: `dns_records.zone_id` is filtered by
> literally every record query and has no index, so those are all full table scans; a composite
> `UNIQUE (zone_id, name, type)` covers that query *and* the uniqueness constraint at once, and I'd
> drop the three redundant `index=True` on primary keys the planner never uses. **Three**, fix the
> N+1: the zone list issues one query per zone to compute `record_count`. **Four**, only then think
> about read replicas or caching — record sets are read far more than written, so they cache well,
> but I'd want to see the query plans first rather than guess.

**9. "What's an N+1 query? Do you have one?"**

> N+1 is fetching N parent rows in one query and then triggering one extra query per parent by
> lazily touching a relationship — 1 + N instead of 1 or 2. Yes, I have one.
> `HostedZone.record_count` is a Python property returning `len(self.records)`, and `records` is a
> lazily loaded relationship, so reading it fires a `SELECT * FROM dns_records WHERE zone_id = ?`
> per zone — loading every full row just to call `len()` on them. The zone list calls it once per
> zone through `ZoneOut.from_orm_with_count`; I measured 5 zones producing 6 queries. The wrinkle is
> that the *sort* path already does it right, with a correlated `SELECT count(*)` scalar subquery —
> the same number computed two ways in one endpoint, only one of them efficient. The fix is to use
> that subquery as a real selected column and delete the property. `selectinload(HostedZone.records)`
> would also fix it in two queries, but still ships every row over just to count them.

**10. "Why `check_same_thread: False`?"**

> Because FastAPI runs plain `def` endpoints — all of mine — in a worker threadpool so they don't
> block the event loop, while SQLAlchemy's connection pool is process-wide. A connection first
> opened on one worker thread gets handed to a different one later, and Python's `sqlite3` driver
> refuses that by default. Disabling the check is safe here because the pool checks a connection out
> to exactly one thread at a time — never *shared* concurrently, just reused across threads — and
> `get_db`'s `try/finally` guarantees it's returned. It's a SQLite-only argument, though: passing it
> to a Postgres driver raises, so it becomes conditional on the URL scheme when I migrate.

**11. "Why the `try/finally` in `get_db`?"**

> Because the session has a pooled connection checked out, and closing it after the `yield` without
> a `finally` never runs when the handler raises — FastAPI throws the exception back into the
> generator at the `yield` point. My handlers raise `HTTPException` constantly: 404s, 409s for CNAME
> conflicts, 422s for bad rdata, all ordinary user mistakes rather than rare crashes. Without
> `finally`, roughly fifteen validation errors would exhaust the default pool of five plus ten
> overflow, and every request after that would hang until `pool_timeout` and then fail. `finally`
> makes the check-in unconditional.

**12. "How do you handle migrations?"**

> Today I don't, properly — and I can tell you exactly what that cost me. `create_all()` at import
> creates missing tables, plus a hand-written `run_migrations()` doing one `ALTER TABLE ADD COLUMN
> owner_id`. But `create_all` never *alters* an existing table, and SQLite's `ADD COLUMN` can't
> attach a foreign key or an index. So the model declares `owner_id` with an FK to `users.id` and
> `index=True`, and my long-lived local database has neither — I confirmed it by compiling the
> metadata and diffing against `sqlite_master`. My README documents the FK too, so the docs are
> wrong as well. Two mitigating facts: the deployed disk is ephemeral, so every boot builds a fresh
> schema from `create_all` and *does* get the FK and index; and the drift only affects databases
> predating the ownership feature. But this is precisely the failure Alembic prevents — `alembic
> revision --autogenerate` diffs models against the live schema and would have caught it on the
> first run. With a durable disk, step one is autogenerate a baseline, `alembic stamp head`, delete
> `create_all` and `run_migrations`, and make `alembic upgrade head` the release command.

**Bonus — "What would you change first?"**

> In order, cheapest-to-highest-impact:
>
> 1. **Add `UNIQUE (zone_id, name, type)`** — closes the TOCTOU race *and* the autoflush duplicate
>    bug *and* removes a full table scan from every record create. One constraint, three fixes.
> 2. **Turn on `PRAGMA foreign_keys`** via a connect-event listener, so the cascade I already wrote
>    actually runs.
> 3. **Fix the N+1** — make `record_count` the correlated subquery the sort path already uses.
> 4. **Drop the three redundant `index=True` on primary keys**, which the planner never uses.
> 5. **Delete the dead code** — `ZoneType`, `RecordType`, `private_zone`. `private_zone` isn't just
>    unused, it actively lies: one zone is `type='Private'` with `private_zone='No'`.
> 6. **Adopt Alembic** before the database ever becomes durable.

### R3.1 A multi-value NS record — how `\n` separation actually looks

Row `id = 1` in `dns_records`, Python `repr` so the escapes are visible:

```
(1, 1, 'vprofile.in.', 'NS', 172800,
 'ns-1.awsdns-1.com.\nns-2.awsdns-2.net.\nns-3.awsdns-3.co.uk.\nns-4.awsdns-4.org.',
 'Simple', 'Default NS record')
```

`zone_id=1` is the **integer** FK → `hosted_zones.id` = 1 = `vprofile.in.`; `name` is the zone apex,
lowercase with a trailing dot; `ttl=172800` is 48 hours, because NS records are cached aggressively;
`value` is four hostnames joined by `\n` — **one row, four values**; `routing_policy` is `Simple`,
comment `Default NS record`.

It was written by `"\n".join([...])` at `backend/app/routes/zones.py:31-36`, and read back apart at
`backend/app/routes/zones.py:223` (`"value": r.value.split("\n")` → a JSON array) and at
`backend/app/routes/zones.py:241-242`, which emits **one BIND line per value** from the single row —
the round trip that shows the encoding is lossless:

```
vprofile.in.                     172800  IN NS     ns-1.awsdns-1.com.
vprofile.in.                     172800  IN NS     ns-2.awsdns-2.net.
vprofile.in.                     172800  IN NS     ns-3.awsdns-3.co.uk.
vprofile.in.                     172800  IN NS     ns-4.awsdns-4.org.
```

### R3.2 A single-value SOA record, for contrast

```
(2, 1, 'vprofile.in.', 'SOA', 900,
 'ns-1.awsdns-1.com. awsdns-hostmaster.amazon.com. 1 7200 900 1209600 86400',
 'Simple', 'Default SOA record')
```

SOA rdata is **space**-separated *within one value* (primary NS, responsible party, serial, refresh,
retry, expire, minimum — validated as exactly 7 tokens at `backend/app/schemas.py:468-482`), while
NS rdata is **newline**-separated *across values*. Spaces separate fields inside one value; newlines
separate values inside a record set. That's the whole encoding rule.
